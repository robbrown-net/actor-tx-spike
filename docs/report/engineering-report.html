The engineering story

How actor-tx-spike went from a three-test Elixir experiment to an observable, policy-driven FX payment orchestrator, and why. Written for someone joining the project: it explains the reasons, not just the code.

1. Where we started

The idea. Rob wanted to learn Elixir, the BEAM and OTP by exploring stateful transaction messages passed around stateful sub-systems, in the spirit of Fred Brooks: pick the most productive high-level language that fits, but keep an escape route (Rust) if performance demands it.

The first spike (built in Cursor):

  • One gen_statem per transaction: queued → awaiting_a → awaiting_b → committed, with compensating → failed.
  • Two fake subsystem GenServers under a supervisor, idempotent per tx_id, with a "crash next request" switch.
  • A disk-backed snapshot store so a node restart could resume in-flight work.
  • Three tests. 76.5% line coverage.

It worked, and it proved the OTP shape: a process per transaction, supervised workers, restart on crash. But the analysis found 12 gaps worth recording because they set the agenda: idempotency lived only in memory; resubmitting after restart re-executed; finished processes never exited; await timeouts crashed the caller; compensation was a stub; the store rewrote everything per write, non-atomically; one corrupt snapshot could stop boot; A and B were hardcoded; the README claimed a vendored toolchain that the repository did not contain.

2. The questions that shaped everything

"Orchestrator or choreography?"

The owner asked us to settle this first, by clarifying the business need. The answers decided it:

AnswerImplication
Money, inventory, legal recordsHalf-done is unacceptable; audit trail and compensation are mandatory
Flow varies per transactionRouting must be data, not code
Parallel fan-out and branchingReal workflow semantics
"Where is transaction X now?"One place must know the whole story
Change flow without redeployingThe flow lives outside the participants
Scale across nodesParticipants addressed logically

→ Orchestration, with flows as declarative data. (ADR 0001.)

"What do the sub-systems actually are?"

The pivotal reframing came next. The sub-systems are facades over unreliable third-party providers: an FX swap and an idempotent payment. They may be fast and cheap, slow, expensive, degraded, stalled, or change behaviour without telling us. The system must weigh cost and speed, keep going when a provider fails, and eventually be self-healing and real-time worldwide, watching CPU, memory, storage and network.

That turned "run A then B" into provider selection under uncertainty. The architecture, the fakes, the health model and the scoring all follow from this.

4. How the design works now

submit ─► Payment (one process per transaction)
            │ quote  ─► Selector ─► Provider.Server ×N ─► adapter
            │ policy: weights, constraints, max bps from best
            ├─ accept ► authorise ► pay        (idempotency key per step)
            ├─ definite failure ─► undo, fail over to next candidate
            ├─ doubt ─► ask provider (status) ─► never guess
            └─ unresolvable payment ─► needs_review
  • Selection (Selector, Policy): concurrent quotes within a deadline; stalled and

quarantined providers are not called; constraints, then a relative cost/speed/reliability score; deterministic ranking; baseline fallback.

  • Provider layer (Provider.Server, Provider.Health): breaker, rolling stats,

bulkhead, enforced timeouts, version-drift quarantine, gradual recovery.

  • Lifecycle (Payment): retries, compensation, failover, reconciliation, escalation.
  • Narrative (Events, Narrative, Panel): every component announces itself; the

dashboard and terminal are projections.

6. Architecture steers (what the owner pushed on)

  • Declarative data over code for flows and policy.
  • "Keep going": the system always starts with a valid result and may only improve it; unavailable providers must be routed around.
  • Single node first, but do not design distribution out.
  • Compensation as real operations and a hard price-distance constraint in policy.
  • Cascading objectives: global → merchant (paid privilege) → special customer, plus weekly standing guarantees.
  • Two-leg lifecycle: quote, accept, authorise, pay, then settlement phases with regional cut-offs (e.g. 18:00 UK local).
  • A sentinel that checks provider version, up-state and response time on a configurable cadence.
  • Gradual recovery rather than snap-back.

Main success scenario

  1. Merchant submits the request.
  2. System acknowledges with a transaction id and starts the transaction.
  3. System asks every callable provider for a quote concurrently, within a deadline.
  4. System discards unusable quotes and ranks the rest under the policy.
  5. System selects the best candidate.
  6. System asks that provider to accept the quote (rate lock).
  7. System asks that provider to authorise the payment (funds hold).
  8. System asks that provider to pay.
  9. System records completion and informs waiters; Merchant reads the outcome.

Glossary

TermMeaning
TransactionOne FX swap and payment for a customer, owned by exactly one process for its whole life.
ProviderA third-party service (FX quote + payment) we do not control. Facaded by an adapter.
QuoteA firm offer with an expiry: rate and fee.
CandidateA quote that passed constraints, with net value, latency and score.
Net valueamount × rate − fee: what the customer ends up with.
EffectSomething that actually happened at a provider: accept, authorise, pay (or an undo).
Idempotency key"<tx>:<provider>:<step>". Reused on retry so a repeat cannot repeat the effect.
Undocancel_accept, void_authorisation, refund: compensating operations keyed by the effect's key.
In doubtWe asked, got no definite answer; the effect may or may not have happened.
ReconcileAsk the provider (status) what it holds for a key.
Needs reviewA state we refuse to resolve by guessing; a human decides.
BaselineA valid default route returned when no quote is usable.
Health stateunknown / healthy / degraded / stalled / quarantined: our view of a provider.
BreakerPer-provider circuit: closed / open / half_open.
QuarantineA provider whose version changed is not trusted until released.
NarrativeThe ordered stream of events describing everything the system does.

Operation contracts (key system operations)

submit(request, providers, policy, opts)

  • Pre: request.amount present; request.id contains no :; providers and policy supplied.
  • Post: a transaction process exists for id (or already existed); a tx_received event was emitted; returns {:ok, id}.

select(request, providers, policy, deadline)

  • Pre: policy valid.
  • Post: every provider is either skipped (state excluded), called, or reported failed; candidates satisfy all hard constraints and max_bps_from_best; ranking is deterministic (score desc, provider id asc); returns within deadline + grace.

step(op, key) (accept, authorise, pay)

  • Pre: previous step succeeded at the same provider; quote not expired.
  • Post: the effect has happened at most once for key; outcome is ok, definite failure, or doubt; doubt is never treated as failure for pay.

compensate(done_steps)

  • Post: each completed step has its undo issued in reverse order, or the transaction is in needs_review.

Principles:

  1. Sampling, not tracing, for resources. One sampler process, fixed cost regardless of load.
  2. In-process aggregation. Counters are cheap atomics / ETS counters; never a message per measurement.
  3. Bounded memory. Ring buffers with fixed capacity; observability must not become the leak.
  4. Tiered retention. Raw → 1 min → 1 h so long-term storage grows slowly and predictably.
  5. Alerts go into the narrative so the same dashboard explains what changed.
  6. Overhead budget: the monitoring layer must stay under ~1% CPU and a fixed memory cap, and is itself measured.

Decisions (ADRs)

ADR 0001: Orchestrated transactions with declarative flows

Status: accepted. Later decisions: ADRs 0002–0006 (safety rules, provider model, observability, tests, toolchain). Date: 2026-10-15

Context

The domain is money / inventory / legal records, so a transaction left half-done is unacceptable. Observed needs:

  • The flow varies per transaction (routing depends on payload and results).
  • Journeys need parallel fan-out/join and branching on results.
  • Operators must be able to ask "where is transaction X right now?".
  • The flow must be changeable without redeploying every subsystem.
  • Subsystems should eventually scale independently / across nodes.

Decision

  1. Orchestration, not choreography. One transaction actor per

transaction owns the journey. Subsystems are participants that react to commands; they do not know the flow.

  1. Flows are declarative data (validated into structs at load time):

steps, dependencies (fan-out/join), branch rules on results, and a compensation per step. The transaction process interprets the data; it contains no hardcoded subsystem names.

  1. Availability over consistency ("keep going"). Every transaction starts

with a valid baseline outcome and may only ever be replaced by a better valid outcome. A failure or partition leaves the best outcome found so far.

  1. Scope: single node first. Distribution is deferred but must not be

designed out (logical subsystem addressing, no node-local assumptions in the message contracts).

  1. Quality gates: 100% automated unit-test coverage; >85% automated

integration-test coverage.

Interpretation of decision 2 (please confirm)

  • Each flow defines a baseline outcome produced at queued without

contacting any subsystem.

  • Each step may yield a candidate outcome; the flow supplies an ordering

(better_than). A candidate replaces the current outcome only if better.

  • Because every intermediate outcome is valid by construction, a transaction

that exhausts retries or loses a participant terminates with its best outcome rather than rolling everything back. Compensation is still required where a completed step's visible effect makes the outcome worse than the baseline.

  • Constraint this puts on subsystems: **every step's effect must itself leave

the system in a valid state**. If a real step cannot guarantee that, it needs a compensation and a stricter flow.

  • Under a future partition both sides may proceed; convergence relies on

idempotent effects plus the deterministic better_than ordering (keep the maximum).

Consequences

  • Transaction becomes a flow interpreter plus an append-only event log.
  • Subsystem contract: command carries tx_id, step_id, attempt; reply is

ok(candidate), rejected(reason) (business) or error(reason) (retry).

  • Idempotency must be durable in subsystems, not an in-memory map.
  • The term-to-file Store is a spike artefact. A real transactional store

(outbox/inbox pattern) is required before production use.

  • Ordering semantics ("better than") become part of the flow schema and need

property-based tests.

Amendment 1 (2026-10-15): the real domain is provider selection, not a sequence

Decision 2 was clarified. The "subsystems" are facades over unreliable third-party providers (initial use case: FX swap + idempotent payment). Providers may be fast and cheap, slow, expensive, degraded, stalled, or change their behaviour without notice. We have no control over them.

This changes the shape of a flow from "A then B" to:

received → quoting → selecting → committing → settled
                │                    │
   (fan-out to N providers,          └─ timeout/unknown → in_doubt → reconciling → settled | failed
    deadline, collect quotes)

Principles

  1. Quote freely, commit once. Fan-out/hedging is safe for quotes (no

effect). Execution has exactly one commit point per transaction at a time. "Keep going" (decision 2) applies to quoting/selection and to choosing the next provider after a definite failure.

  1. A timeout on commit is not a failure, it is in_doubt. Before trying

another provider we must reconcile the first (query by idempotency key) or rely on a provider-honoured idempotency key. Never double-pay.

  1. Best-outcome-so-far lives in the pre-commit phase. The baseline is a

valid default route (e.g. last known-good provider); quotes can only improve it, judged by a scoring policy. After commit we only reconcile.

  1. Providers are modelled, not trusted. Each has our view of its state

(healthy | degraded | stalled | unknown | quarantined), observed version / payload fingerprint, rolling latency and error rate, and cost basis.

  1. A sentinel keeps the model honest: scheduled probes (configurable

interval, e.g. 6h) plus passive observation of live traffic, detecting version/shape drift, latency drift and availability, feeding a circuit breaker.

  1. Scoring is policy as data: weights/constraints over cost, latency,

reliability and quote validity window; hard constraints (e.g. quote must not expire before commit).

  1. Resource budgets are first-class: bounded in-flight work per provider

(bulkhead), bounded mailboxes, log compaction/retention, telemetry on CPU, memory, storage and network. Hedging has a network/rate-limit cost and is budgeted.

Provider adapter contract (behaviour)

  • quote(request) -> {:ok, quote} | {:rejected, why} | {:error, transient} | :timeout
  • execute(quote, idempotency_key) -> {:ok, receipt} | {:rejected, why} | {:error, transient} | :in_doubt
  • status(idempotency_key) -> {:ok, receipt} | :not_found | :unknown
  • probe() -> version / up-state / latency sample

Open questions

  • Do providers support lookup by idempotency key (resolves in_doubt)?
  • Are quotes firm with an expiry, or indicative?
  • Is the scoring objective global or per customer/request?
  • Are the FX and payment legs one provider call or two (second commit point)?

Amendment 2 (2026-10-15): lifecycle, cascading policy, settlement deadlines

Answers to the open questions:

  • Providers can look up a payment by idempotency key, but not in real time

yet. in_doubt resolution therefore needs an asynchronous reconcile path (poll/schedule) for now; revisit later.

  • Quotes are firm with an expiry: expiry is a hard constraint on every

later step.

  • The FX leg and the payment leg are separate provider calls, so a

transaction has several effectful steps, not one commit point.

Lifecycle (supersedes the single-commit sketch)

quote (no effect, firm+expiry) → accept quote (locks rate)
  → authorise payment (hold) → make payment
  → settlement phases, each with a regional cut-off (e.g. 18:00 UK local for UK payouts)
  • quote is hedgeable. accept, authorise, pay and settle are

effectful: each has its own idempotency key, own in-doubt handling and a defined compensation (cancel/unwind, possibly at a cost). Compensation is therefore real again after the first effectful step.

  • Each step carries a deadline: quote expiry for accept; regional local-time

cut-off for settlement. Deadlines drive scheduling priority. Local-time cut-offs need a timezone database (e.g. tzdata); this is the spike's first external dependency.

Cascading objectives (policy as data)

Resolution order, most specific wins, others inherited: global default → merchant policy (optional, paid) → special customer policy.

A merchant may also hold a standing guarantee (e.g. weekly guaranteed rate). Per transaction we may route better than the guarantee; the difference is our margin or exposure and must be accounted for per guarantee period (ledger concern, deferred past the spike's core).

Amendment 3 (2026-10-15): commit-step rules, undo operations, observability

Decided:

  • Compensation is modelled as real provider operations on the adapter

(cancel_accept, void_authorisation, refund), each keyed by the same idempotency key as the effect it undoes, idempotent, and safe for a key whose effect never happened.

  • Doubt handling (Payment): status lookup first. Unconfirmed

accept_quote / authorise are cancelled by key and failed over. An unconfirmed pay is never failed over: bounded reconcile attempts, then needs_review. Failed compensation also ends in needs_review.

  • Policy gains max_bps_from_best (hard constraint applied before scoring).
  • Observability is a first-class requirement. All components emit

ActorTxSpike.Events; the dashboard and terminal narrative are projections of that single stream. Observing must never slow or break the system (fire-and-forget, bounded buffer).

ADR 0002: Commit-step safety rules

Status: accepted · Date: 2026-10-15 · Supersedes the "quote freely, commit once" sketch in ADR 0001 Amendment 1

Context

The real lifecycle has several effectful provider steps (accept, authorise, pay) and providers can answer slowly, wrongly or not at all. Naive failover on timeout risks paying twice; naive "fail" on timeout risks leaving money held.

Decision

  1. Quoting is free and hedged. Every later step is effectful and carries its own

idempotency key "<tx>:<provider>:<step>", reused on retry.

  1. Definite failures (technical error): bounded retry with the same key. Then

compensate what was done at that provider and fail over to the next-ranked quote.

  1. Doubt (timeout, answer lost): ask the provider (status(op, key)) before doing anything else.
  2. Accept / authorise (reversible): if still unconfirmed, cancel by key (idempotent, defeats a late effect) and fail over.
  3. Pay: never fail over while in doubt. Reconcile a bounded number of times, then needs_review.
  4. Compensation is a first-class provider operation (cancel_accept, void_authorisation, refund), keyed by the effect's key, idempotent, and safe for a key that never took effect.
  5. Compensation that cannot complete is escalated (needs_review), never ignored.

Alternatives considered

  • Fail over on any timeout: simplest, unsafe for money.
  • Retry pay on a different provider with a new key: double-payment risk.
  • Two-phase commit across providers: providers do not support it.

Consequences

  • A small, explicit set of states a human may have to resolve.
  • Providers must support idempotent keys and undo-by-key (assumed; to be validated against real APIs).
  • status is allowed to be stale, so "not found" means "not known yet".
  • The randomised storm test asserts these rules as invariants.

ADR 0003: Providers are modelled, not trusted

Status: accepted · Date: 2026-10-15

Context

Providers are third parties that decay, stall, are delayed or change behaviour without notice. The system must keep serving ("keep going") and protect money.

Decision

  • Each provider sits behind a Provider.Server with a circuit breaker, a rolling

health window, a bulkhead (max in-flight) and enforced per-call timeouts.

  • Health is a pure model (Provider.Health): unknown / healthy / degraded / stalled / quarantined.
  • Version drift quarantines a provider until released; behaviour change on a money path is not trusted.
  • Recovery is gradual: after a successful half-open probe, history is cleared and

the provider stays degraded until recovery_successes consecutive successes.

  • Selection never calls providers whose state the policy excludes.
  • A sentinel probes on an interval; in the spike it is a demo timer.

Alternatives considered

  • Trust provider responses: unsafe.
  • Reset history on recovery then declare healthy: a single lucky probe re-admits full traffic (rejected by the owner in favour of gradual).
  • Let old errors age out only: a quiet provider never recovers.

Consequences

  • The model is deterministic and exhaustively testable (time is injected).
  • Quarantine needs an operator or sentinel policy to release; review tooling is future work.

ADR 0004: Observability is a first-class requirement

Status: accepted · Date: 2026-10-15

Context

The owner reported the system felt like a black box and wants to see and feel it run: transactions unfolding, services receiving, processing and responding.

Decision

  • Every component announces what it does through one stream, ActorTxSpike.Events.

Each event has a human message and structured data.

  • The terminal narrative and the dashboard are projections of that single stream;

neither has private knowledge.

  • Providers (fakes now, real adapters later) narrate their own side: received, processing, responded.
  • Emission is fire-and-forget with a bounded buffer: observing must never slow or break processing.
  • The dashboard is also a control surface for the demo world so behaviour can be provoked.
  • The dashboard server is dependency-free (OTP sockets, SSE) and loopback-only.

Consequences

  • Narrative is not durable yet; persistence belongs to the Phase 3 log.
  • Resource and performance metrics are a separate design (07).
  • Control endpoints are unauthenticated: acceptable only because of loopback binding.

Dashboard motion principles (added 2026-10-15)

Motion explains what just changed; it never decorates. Contributed from the owner's collaborator notes.

  • One easing curve (cubic-bezier(.2,.8,.2,1)), short durations (0.15 / 0.3 s; 0.8 s for reveals), small distances (5–8 px).
  • Persistent DOM: provider cards and transaction cards are created once and patched in place, so CSS transitions fire. Never rebuild with innerHTML on every event.
  • The story pane is append-only; new events rise in, history replayed on connect does not animate.
  • Meaningful cues only: provider state change flashes its card in the state colour; a finished transaction flashes green / red / amber; one pulsing "live" indicator.
  • Reduced motion is honoured (prefers-reduced-motion) and there is a "Motion: on/off" switch, remembered per browser.
  • Errors surface as a toast with the server message, not a blocking dialog.

ADR 0005: Test strategy and quality gates

Status: accepted · Date: 2026-10-15

Context

Owner requirement: 100% automated unit-test coverage and >85% automated integration-test coverage.

Decision

  • test/unit and test/integration are separate suites with separate gates:

mix test.unit (100% line coverage) and mix test.integration (>85%).

  • Decision logic is kept pure (Policy, Health) so it is cheap to test exhaustively.
  • A fake provider is scriptable at runtime (modes, mode lists, latency, drift) and records every effect.
  • A randomised fault-storm test asserts money-safety invariants (never paid twice, failed never paid, failovers fully undone).
  • Tooling modules (Demo, Demo.Handler) are excluded from the unit gate only; the thin Mix.Tasks.Demo entry point is excluded everywhere. Both exclusions are explicit in mix.exs.
  • Static analysis: Credo (strict), Sobelow, mix_audit as dev-only dependencies.

Known limits

  • Coverage is line-based; branch/mutation measurement is still to do.
  • No system-test suite (boot the real demo, drive over HTTP/SSE) and no tagged regression pack yet.
  • Randomised tests use a fixed seed per run but concurrency makes interleavings vary.

Consequences

  • Refactors are safe; gates fail loudly.
  • 100% line coverage is necessary, not sufficient: the invariant tests carry the real weight.

ADR 0006: Toolchain and dependencies

Status: accepted · Date: 2026-10-15

Context

The owner's older Intel MacBook is no longer supported by Homebrew.

Decision
